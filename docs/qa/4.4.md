### BUG-1 (S2): Saves never reach the account
- **Where:**
  - `lib/features/saved/application/saved_providers.dart:76`;
  - `lib/features/auth/application/auth_providers.dart:56` (the guest sync).
- **Cause:** both insert `{'deal_id': id}`. But `saves.user_id` is `not null` with **no default** (`20261029120400_user_activity.sql:24`), and the policy "saves: add own" checks `user_id = auth.uid()`.
  - As a shopper in Postgres, `insert into public.saves (deal_id) …` gives `42501: new row violates row-level security policy for table "saves"`.
  - With `user_id` set, the same row is accepted.
  - The app catches the error and logs "Could not sync a saved deal", so nothing shows.
- **Effect:**
  - A signed-in shopper's saves exist only on that phone. "Keep your saves … on any phone" (sign-in text) isn't true.
  - Guest saves never move into the account at sign-in.
  - `trending_deals` ranks by recent saves (`private.recent_save_counts`), so in production Trending today would never see a save.
- **Why the tests missed it:** the developer's tests pass because `DemoGateway.insert` accepts any row.
- **Reproducers:**
  - `deal_page_qa_test.dart`: "signed in, a save reaches the account" and "guest saves reach the account at sign-in" (`RulesGateway` applies the column rules);
  - `qa_deal_page_and_follows.test.sql`: TODO "a save as the app sends it…".
- **Suggested fix:**
  - send `'user_id': user.id`, as the delete already does;
  - or, more robustly, a new migration with `alter table public.saves alter column user_id set default auth.uid()` (as `reports.reporter_id` has).
  - The same applies to `follows` (4.5 BUG-1).
  - Then make the demo gateway enforce it, or run the data tests against `RulesGateway`.

### BUG-2 (S2): A save can wipe every earlier save
- **Where:** `saved_providers.dart:25–28` (`build` returns `[]` and loads in the background) and `:54–65` (`toggle` writes `state` to `saved.v1`).
- **Cause:** `toggle` writes the whole list as the provider knows it, whether or not the file has been read.
  - **Read failed** (a transient storage error, like 4.1 BUG-1): `state` stays `[]`, so the next save writes `[new]` over the file. Every earlier save is gone for good.
  - **Read not finished yet** (cold start straight into a shared deal link, slow storage): the file is overwritten with `[new]`. The merge in `_load` then fixes the screen, but not the file, so the earlier saves are gone after the next restart.
- **Expected:** earlier saves survive. Don't write before the file is known; or merge before writing; or, as `PreferencesController` now does, keep changes in memory until a re-read succeeds.
- **Severity:** S2, as for 4.1 BUG-1: data the shopper chose is lost, silently.
- **Reproducers:** `deal_page_qa_test.dart`, "a failed read of the saved file, then a save…" and "a save made before the saved file was read…". Both end with only the new deal on the phone.

### BUG-3 (S3): Saves come back after account deletion
- **Where:** `saved_providers.dart:25` (nothing resets the provider). `_forgetThisPhone` (`delete_account_screen.dart`) clears the store and resets the preferences, but `savedDealsProvider` keeps its list in memory.
- **Steps:**
  1. Save two deals.
  2. Delete the account and onboard again.
  3. Save another deal.
- **Expected:** the phone holds the new save only ("Local data goes too").
- **Actual:** `saved.v1` holds all three. The deleted account's saves are written back to disk.
- **Reproducer:** "after the account is deleted, the next save does not write the old saves back".
- **Suggested fix:** watch `onboardedProvider` in `build` (as `NearMeController` now does), or invalidate it in `_forgetThisPhone`.

### BUG-4 (S3): Large chains lose their local outlets
- **Where:** `lib/features/deals/data/backend_deal_repository.dart:171–178` and `:204–215`.
- **Cause:** the brand's outlets are read **first** (the first 100 by name) and **then** filtered by the local deal's target cities and areas.
- **Steps:** a brand with 145 Karachi outlets and 5 in Quetta, and a deal targeting only Quetta.
- **Expected:** "Where to use it" lists the 5 Quetta outlets.
- **Actual:** "No outlets" (all 100 rows read are in Karachi).
- **Reproducer:** "a local deal of a chain with more than 100 outlets…".
- **Suggested fix:** read the targets first and filter the outlet query by their `city_id` (`inList`), then apply areas.
- For nationwide deals, consider ordering by the shopper's city first (today a Karachi shopper sees the first 100 outlets alphabetically, from any city).

### BUG-5 (S4): A note ending in an emoji at the cap fails
- **Where:** `lib/features/deals/application/report_providers.dart:54`.
- **Cause:** `text.substring(0, 500)` cuts in UTF-16 units, while the field's `maxLength: 500` counts characters. So 499 letters and "😀" (501 units) are allowed, and then cut inside the emoji.
- **Effect:** the lone surrogate makes Postgres reject the row: checked on Postgres 16, `json_populate_recordset` raises 22P02 "Unicode low surrogate must follow a high surrogate". The shopper sees an error.
- **Reproducer:** "a long note ending in an emoji at the cap still sends…".
- **Suggested fix:** cap by characters (`text.characters.take(500).toString()`); the DB check counts code points, so this fits.

### BUG-6 (S4): Save doesn't read as a toggle
- **Where:** `lib/features/deals/presentation/deal_detail_screen.dart:289–291`.
- **Cause:** `Semantics(toggled: saved, child: OutlinedButton…)` makes a separate node; the button's own node has no toggled state (`isToggled == Tristate.none`).
- **Effect:** the label still changes ("Save" / "Remove from saved"), so the state is heard. But not as on/off, unlike the Follow button.
- **Reproducer:** "Save reads as a toggle…".
- **Suggested fix:** `Semantics(button: true, toggled: saved, label:…, excludeSemantics: true, onTap:…)`, as in `FollowButton`.

#### R2-1 (S4): A tap during loading is replayed as its opposite
- **Where:**
  - `lib/core/storage/stored_string_list.dart:101–107`: a change made while the file loads is kept as a function and replayed on the file.
  - `lib/features/saved/application/saved_providers.dart:43–44`: the toggle's function decides "save or unsave" each time it runs.
- **Steps:**
  1. Deal X is saved on disk.
  2. Open it before the file has loaded (the page shows "Save").
  3. Tap Save.
- **Expected:** X stays saved.
- **Actual:**
  - The tap saves X in memory, and the mirror inserts it on the server.
  - Then the replay finds X in the file and removes it.
  - The phone ends up with X unsaved (also on disk) while the account has it saved.
- **Severity:** the window is one read, so S4.
- **Reproducer:** `deal_lists_r2_qa_test.dart`, "tapping Save on a deal that is already saved, before the file has loaded…".
- **Suggested fix:** record the intent ("ensure saved" / "ensure removed"), not a toggle, and mirror only what the final list says.

#### R2-2 (S3): Saves made while storage failed are lost
- **Where:** `stored_string_list.dart:108–114`. After a failed read, each change re-reads the file. When that succeeds, only **this** change is applied to the file, so the changes made in memory while it was unreadable are dropped.
- **Steps:**
  1. The file read fails.
  2. Save deal 2 (shown as saved; the re-read fails too).
  3. Save deal 3 (the re-read works).
- **Expected:** the file holds 1, 2 and 3.
- **Actual:** it holds 1 and 3. Deal 2, shown as saved, is gone from the screen and from the phone.
- **Reproducer:** "saves made while the file was unreadable survive once it reads again".
- **Suggested fix:** keep the in-memory changes as a pending list (as during the first read) and replay all of them when a read finally works.

#### R2-3 (S4): Mixed targets fall back to a city-wide read
- **Where:** `lib/features/deals/data/backend_deal_repository.dart:235–241`. When any target is city-wide, the outlet query filters by **all** target cities, including a city that was only targeted for one area.
- **Example:** a chain with 145 other Karachi outlets named before its Clifton ones, and a deal for "all Quetta" plus "Clifton, Karachi". The first 100 by name are all non-Clifton Karachi outlets, so the deal lists 0 outlets.
- **Reproducer:** "a city-wide target plus an area in a big chain's home city…".
- **Suggested fix:** two reads (city-wide cities, and areas), or an `or` filter.
