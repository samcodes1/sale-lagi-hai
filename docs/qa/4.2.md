### 4.2-A1 (S2): the fresh-sign-in rule for deletion uses `last_sign_in_at`, which every token refresh bumps
- **Area / file:** `supabase/functions/delete-account/account.ts:37-38` (and `verifyUser`, `account.ts:72-79`)
- **Environment:** the function against mocked HTTP; Supabase Auth behaviour read from `supabase/auth` master
- **Steps to reproduce:**
  1. A shopper signs in once, then uses the app for days. supabase_flutter refreshes the session on launch and about hourly; a stolen refresh token can be refreshed the same way.
  2. Within 5 minutes of any refresh, call `POST /functions/v1/delete-account` with the new access token.
- **Expected:** `403 reauth_required` unless the shopper actually authenticated (OTP or Google) in the last 5 minutes. ACCOUNTS.md says the rule exists "so a stolen or left-open session can't delete the account".
- **Actual:** `200 deleted`. Supabase Auth's refresh grant (`GrantRefreshTokenSwap` → `createRefreshToken`, `internal/models/refresh_token.go:205`) calls `user.UpdateLastSignInAt`. The `/auth/v1/user` answer therefore shows `last_sign_in_at` ≈ now after every refresh. This is the default path: `refresh_token_algorithm_version` defaults to 0, which uses the swap.
- **Evidence:** `supabase/functions/delete-account/qa_account.test.ts`, test "QA BUG 4.2-A1" (fails: `deleted` instead of `reauth-required`).
- **Severity rationale:** a security control on an irreversible, Play-required action doesn't do what it claims. It needs an already-compromised or left-open session, so S2 rather than S1.
- **Suggested fix:** after `/auth/v1/user` accepts the token, read the token's `amr` claim and use the latest `timestamp` among the sign-in methods (`otp`, `oauth`/`id_token`, `password`). Refreshes don't change it, and a new OTP or Google sign-in creates a new session with a new `amr`. Require `now - amr_ts ≤ 5 min`, and treat a missing or garbled claim as `reauth-required`. Keep the 5-minute rule in `DemoAuthRepository`, which already measures sign-in time.
- **Regression test:** QA's A1 test (a token whose `amr` is 2 h old but whose `last_sign_in_at` is now).

### 4.2-A2 (S2): the fresh sign-in before deletion accepts any account, and the retry deletes that one
- **Area / file:** `lib/features/auth/presentation/delete_account_screen.dart:63-71`; `sign_in_screen.dart:49-54` (the number is prefilled but editable), `:261-281` (Google is offered in re-sign-in too), `:156-165`
- **Environment:** `e8c4177`, demo backend, any locale or size
- **Steps to reproduce:**
  1. Sign in as 0300 1234567 (A). Wait more than 5 minutes.
  2. Profile → Delete account → Delete my account → confirm. "Confirm it's you" opens.
  3. Change the number to 0333 7654321 (B) and enter B's code. (Or, as a phone user, tap "Continue with Google".)
- **Expected:** re-sign-in only confirms A. Another account is refused, and A is the account deleted.
- **Actual:** the screen pops `true` for any account, and `deleteAccount()` runs for whoever is now signed in. B (or a brand-new Google account) is deleted. A, with all its data, stays on the server. The app then clears this phone and says "Your account was deleted."
- **Evidence:** `test/qa/auth_flow_qa_test.dart`, "QA BUG 4.2-A2" (fails: `deleted [...0002] but the request was for [...0001]`).
- **Severity rationale:** the core Play-required flow can silently delete the wrong account and leave the shopper's own data in place while saying it is gone.
- **Suggested fix:** in `_delete()`, keep `auth.currentUser!.id` from before re-sign-in, and retry only if the id is unchanged. Otherwise sign out the new session and show an error. In `SignInScreen(reauth: true)`, make the number read-only for phone users, and offer only the method the account uses (hide Google for phone users and the phone field for Google users).
- **Regression test:** QA's A2 test.

### 4.2-A3 (S3): leaving sign-in while the code is checked signs in without the guest sync
- **Area / file:** `sign_in_screen.dart:119` (`if (!mounted) return;`) and `:156-157`. The sync runs only from the widget.
- **Steps:** on the code step, enter the code, then press Back before the check returns.
- **Expected:** the shopper is signed in (the server accepted the code), and the guest's city, language and brands sync.
- **Actual:** they are signed in, but `guestSyncProvider` never runs and nothing says so. Per ACCOUNTS.md the next try is the next sign-in, which a long-lived session may never reach. Workaround: sign out and in again.
- **Evidence:** `test/qa/auth_flow_qa_test.dart`, "QA BUG 4.2-A3" (fails: `syncCalls` is 0).
- **Suggested fix:** start the sync from the application layer when `userChanges` goes from `null` to a user, not from the widget. Also, or instead, block Back while `_busy` (`PopScope(canPop: !_busy)`).

### 4.2-A4 (S3): a deleted account is reported as failed when `/logout` then fails offline
- **Area / file:** `lib/features/auth/data/supabase_auth_repository.dart:128` (`await _auth.signOut()` inside the guarded block after a successful `invoke`)
- **Steps:** the function answers 200, then the connection drops before `POST /auth/v1/logout`.
- **Expected:** `Success(deleted)`. The account is gone, so the phone is cleared and returns to onboarding.
- **Actual:** gotrue rethrows the network error, which isn't 401/403/404, and `deleteAccount()` returns `Failure(offline)`. The page shows an error and keeps this phone's preferences and cache. The local session is already removed, so the shopper is a guest whose phone still remembers everything, and the delete page is now closed to them. Workaround: clear the app's data.
- **Evidence:** `test/qa/auth_session_qa_test.dart`, "QA BUG 4.2-A4" (fails: `Failure(AppFailure(offline))`).
- **Suggested fix:** once the function returns 200, treat sign-out errors (Supabase and Google) as non-fatal. Catch them, log the failure code only, and return `deleted`.

### 4.2-A5 (S4): a double tap on "Send code" sends two codes
`sign_in_screen.dart:76-87`: `_sendCode` has no `_busy` guard (`_verify` has one), so two taps in one frame send two SMS codes. With Supabase the second gets 429 and shows "too many tries" on top of the code step. Fix: `if (_busy) return;` at the top. Reproducer: `auth_flow_qa_test.dart` "QA BUG 4.2-A5" (skipped; fails unskipped: 2 codes).

### 4.2-A6 (S4): "Change number" skips the 60-second resend wait
`sign_in_screen.dart:324-327` cancels the ticker, and "Send code" for the same number is then enabled at once. The server's own limit (Supabase `sms.max_frequency`, 5/hour in the demo) still applies. Fix: remember the last send per number and keep the wait. Reproducer: "QA BUG 4.2-A6" (skipped; fails unskipped: 2 codes).

### 4.2-A7 (S4): system Back on the code step leaves sign-in instead of returning to the number

### 4.2-A9 (S4): in Urdu, the signed-in number on Profile sits on the left edge

### 4.2-A12 (S4): phone numbers inside sentences break across lines at 200% text

### 4.2-A13 (S4): `+92 0300…` and numbers pasted with RLE/PDF controls are refused

## Security review (step 10)
| Item | Result | Evidence |
|---|---|---|
| Delete someone else's account | PASS | The user comes only from Auth's answer for the bearer token. A body or query `user_id` is ignored, a forged token is rejected by Auth, and nothing else runs (`qa_account.test.ts`) |
| Delete without a fresh sign-in | **FAIL** | A1 (refresh bumps `last_sign_in_at`) and A2 (re-sign-in as another account) |
| Failing closed | PASS | Wrong method → 405 (GET, PUT, DELETE, OPTIONS). Missing, malformed, `bearer`, double-space or more than 4096 chars → 401. `http://` URL, short or missing key → 500. A non-array file list throws before any delete. An Auth answer without a string id → unauthorized |
| Ordering and partial failure | PASS | Batches of ≤100 per bucket, every file before the user. A failure in batch 2 leaves the user in place, and a retry finishes the job (idempotent) |
| Log hygiene | PASS | Five error shapes, including messages carrying an id, phone or token after a colon, a fetch `TypeError` with the admin URL, a non-Error throw and a JSON error: no id, phone or token reaches `console.error`. App side: `AppUser.toString()` holds no PII, the sync failure logs only `failure.code`, and `LogRedactor` covers `+92…`, `03…` and `3xx…` numbers |
| `sync_guest_preferences` abuse | PASS | Anon refused (grant and 42501). Invoker rights, so RLS hides inactive brands. Only the caller's profile and follows change. Null, duplicate, two-dimensional and 200 unknown ids are handled, 201 is refused. Unknown city → 23503; empty or unknown language → 23514. A business member can follow their own inactive brand (RLS shows it to them), which ACCOUNTS.md's "only active brands" doesn't mention |
| `prepare_account_deletion` reachability | PASS | `execute` only for `service_role`; none for PUBLIC, anon or authenticated (`aclexplode`). A shopper, anon and a moderator with MFA all get 42501. `search_path=""`, security definer |
| Storage ownership | PASS (stub) | Only the leaver's files in `deal-images` and `brand-logos` are handed over (deal image and brand logo). Another owner's file keeps its owner. Only private files are listed. See recommendation 3 for the edge cases |
| OTP field privacy | S4 | `oneTimeCode` autofill, no suggestions or autocorrect, LTR. Personalised learning still on (A8) |
| Google client ID | PASS | `^[0-9]+-[a-z0-9]+\.apps\.googleusercontent\.com$` only, so a `GOCSPX-` secret, a JWT or a URL is a config error. Empty hides Google. `app_config_test.dart` covers it |

## Deletion correctness (database)
`supabase/tests/database/qa_accounts.test.sql` builds a leaver with a row in every table that references `auth.users`. The leaver is the **last owner** of a business they created that staff then **suspended**, and an editor of another business. They also have a moderator role and a role they granted to someone, follows, saves, cards, alert preferences, a notification, a report they filed and one they resolved, a pending submission and one they reviewed, a deal and a placement they created, a push token, a queued push, and files in all four buckets.

The test then runs `prepare_account_deletion` as `service_role`, deletes the listed files, and deletes the user as `supabase_auth_admin` (made the owner of `auth.users`, as in Supabase). Results:
- **Nothing blocks the deletion.** `keep_an_owner` skips users that are gone, and the business guard trusts the cascade because RI actions run as the table owner.
- **Removed:** profile, alert_prefs, follows, saves, user_cards, notifications, push_tokens, push_outbox, user_roles and business_members. No storage object is left owned by the leaver.
- **Kept without the id:** `businesses.created_by`, `deals.created_by`, `placements.created_by`, `user_roles.granted_by`, `reports.reporter_id`/`resolved_by` and `submissions.submitter_id`/`reviewer_id`. The suspended business stays, ownerless, for staff to reassign.
- A moderator can still reject the orphaned pending submission (`notify_submitter` skips a null submitter).
- **Recorded:** `audit_log` keeps the leaver's uuid in `old_data` for the removed role and membership rows (see recommendation 4).

Local data: after deletion, `keyValueStore.clear()` removes every `slh.` key (preferences, saved locale, JSON cache) and preferences reset to a first launch. The router returns to onboarding. Checked in the developer's flow test (`h.store.values` is empty) and in the web build (`after-delete_*` shots).

## Recommendations (non-blocking)
1. **Guest sync retry.** One failed `sync_guest_preferences` call is never retried while signed in, and "sync next time" in ACCOUNTS.md means the next sign-in. Retry on the next launch or reconnect, and stop syncing once it has succeeded.
2. **Sign-out failures are silent.** `profile_screen.dart` ignores a failed `signOut()`. A guest who signs in after someone else signs out on the same phone also syncs the previous person's on-phone brands into their account. Consider clearing the follows on sign-out, or asking first.
3. **Storage edge cases** (verify on the full stack in CI):
   - `prepare_account_deletion` matches only `owner_id`. Also match `owner = target` for objects where only the legacy `owner` column is set.
   - Also list files under `<uid>/` in the private buckets that someone else wrote (for example a server-side resize), so no personal photo outlives the account.
   - Check that the `postgres` role may still `update storage.objects` on the current Supabase storage schema.
4. **Audit log.** `audit_log.old_data` keeps the deleted user's uuid. It is pseudonymous, but say so in the privacy policy and the Data safety form, or scrub `user_id` from `old_data` on deletion.
5. **CORS.** `delete-account` has no CORS or `OPTIONS` handling. That's fine for Android, but the Phase 9 web deletion page will need it.
6. **Unauthorized after a lost reply.** If the 200 is lost and the shopper retries, Auth answers 403/401 for the deleted user, and the app shows "unauthorized" while still signed in until the next refresh. Map 401 from `delete-account` to a sign-out as well.
7. **Coverage gaps.** Developer-only coverage of domain and application was 89.0%, below the 90% gate, and the guest-sync failure path was untested. Keep QA's tests, or add equivalents to `test/features/auth/`.
8. **ACCOUNTS.md accuracy.** "It runs once … only follows active brands" holds for plain shoppers only (members see their inactive brands). The re-auth paragraph should describe the `amr`-based check after A1 is fixed.
