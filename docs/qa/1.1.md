#### BUG-1 (S2): Android flavor builds fail on AGP 9, which disables `resValues` by default
- **File:** `android/app/build.gradle.kts:39`, `:45`, `:49` (`resValue("string", "app_name", …)`). `android/app/src/main/AndroidManifest.xml:3` depends on it (`android:label="@string/app_name"`).
- **Steps:** `flutter build apk --debug --flavor dev --dart-define-from-file=env/dev.json`, which is exactly what CI `build-android` runs for all 3 flavors.
- **Expected:** the APK builds and installs with the flavor's launcher name.
- **Actual (predicted, not run here):** Gradle configuration fails because the product flavors define custom resource values while the feature is disabled. Evidence:
  - `android/settings.gradle.kts:22` uses AGP **9.1.0**. The official AGP 9.0 release notes (developer.android.com/build/releases/agp-9-0-0-release-notes) list `android.defaults.buildfeatures.resvalues`, "Enables resValues in all subprojects", as changing **true → false**, with the fix "set `android { buildFeatures { resValues = true } }`".
  - Neither `android/gradle.properties` nor `build.gradle.kts` enables it, and `grep -ri "resvalue\|buildfeatures"` over `/opt/flutter/packages/flutter_tools` finds nothing, so the Flutter Gradle plugin does not enable it either.
  - A third-party write-up checked against Flutter 3.44 + AGP 9.0.1 reports this exact failure for `resValue`-based flavor names.
- **Impact:** all 3 `build-android` CI jobs fail, and nobody can build or run the app on Android in any flavor. This breaks the gate criterion "the app boots in every flavor".
- **Suggested fix:** add `buildFeatures { resValues = true }` inside `android { … }` in `android/app/build.gradle.kts`. Alternatively, drop `resValue` and use `manifestPlaceholders["appName"] = "SLH Dev"` with `android:label="${appName}"`. Confirm with the first CI run.

#### BUG-2 (S3): The secret-key check only runs at app start, so the secret is already in the binary
- **File:** `lib/app/config/app_config.dart:22-27` (validation happens at runtime). `.github/workflows/ci.yml:70-74, 86-87` (no validation before the build).
- **Steps:** create a define file with `"SUPABASE_ANON_KEY": "sb_secret_QASENTINEL123"` and run `flutter build web --release --dart-define-from-file=<file>`, then `grep -c sb_secret_QASENTINEL123 build/web/main.dart.js`.
- **Expected:** the build is refused, or at least CI/tooling catches it before an artifact exists.
- **Actual:** the build succeeds (exit 0) and the grep finds the secret (`1`) in `main.dart.js`. The app only shows the error screen when it is launched, and anyone who downloads the artifact can extract the key. The same applies to APKs. The CLAUDE.md promise "AppConfig rejects secret keys at startup" is true, but it does not stop the key from leaking.
- **Suggested fix:** add `tool/check_env.dart`, which loads `env/<flavor>.json`, runs `AppConfig.fromMap` and exits non-zero on problems. Run it in CI before every `flutter build`, and wrap local release builds in a script that calls it first.

#### BUG-3 (S3): Secret-key detection is a denylist
- **File:** `lib/app/config/app_config.dart:98-111`
- **Steps:** `AppConfig.fromMap` with `SUPABASE_ANON_KEY` = a JWT with `role: supabase_admin`, or any non-Supabase secret such as `sk_live_51H…` (see `test/qa/app_config_qa_test.dart`, group "secret-key detection is a denylist").
- **Expected:** only a publishable key is accepted: `sb_publishable_…`, or a legacy JWT whose `role` is `anon`.
- **Actual:** both are accepted, because only `sb_secret_…` and `role == service_role` are rejected. The detection itself is robust: padding, URL-safe characters, a `Bearer ` prefix, whitespace and malformed or huge input are all handled without crashing (verified by QA tests).
- **Suggested fix:** switch to an allowlist. Accept a key if it starts with `sb_publishable_` or is a 3-part JWT with `role == 'anon'`; otherwise add the problem "SUPABASE_ANON_KEY is not a publishable key".

#### BUG-4 (S3): The Android `--flavor` is not cross-checked against the Dart `FLAVOR`
- **File:** `lib/app/config/app_config.dart:22-46`
- **Steps:** `flutter build apk --flavor prod --dart-define-from-file=env/dev.json` (from reading the code; the APK cannot be built here).
- **Expected:** a mismatch is reported, either on the config error screen or at build time.
- **Actual:** you get an app with the prod app ID `pk.salelagihai.app` and the prod launcher label "Sale Lagi Hai!" but dev config. Once a backend exists, it would point at the wrong Supabase project, or a "prod" install would talk to dev.
- **Suggested fix:** in `fromEnvironment`, pass `appFlavor` (from `package:flutter/services.dart`, set by `--flavor`). In `fromMap`, add a problem when `appFlavor != null && appFlavor != FLAVOR`. `appFlavor` is null on web, so skip the check there.

#### BUG-5 (S3): CI actions are pinned to mutable tags
- **File:** `.github/workflows/ci.yml:23, 26, 33, 34, 46, 58, 59, 63, 80, 81`
- **Expected:** every action, at least the third-party ones (`subosito/flutter-action`, `gitleaks/gitleaks-action`), is pinned to a full commit SHA with a version comment.
- **Actual:** `@v4` and `@v2` tags. `gitleaks/gitleaks-action@v2` also receives `GITHUB_TOKEN`. A moved or compromised tag would run arbitrary code in CI. The impact is limited by `permissions: contents: read` (set correctly at the top level, and the workflow uses `pull_request`, not `pull_request_target`).
- **Suggested fix:** pin by SHA, for example `actions/checkout@<sha> # v4.x.y`, and add `.github/dependabot.yml` for `github-actions` to keep the pins up to date.

#### BUG-6 (S4): The app name is defined in several places that disagree

### Recommendations (non-blocking)
1. **INTERNET permission:** `android/app/src/main/AndroidManifest.xml` has no `<uses-permission android:name="android.permission.INTERNET"/>`. It only exists in the debug/profile manifests, so **release** builds will not be able to reach Supabase. Add it before Phase 2/4 work lands, or as part of 1.7.
2. **Release signing:** `android/app/build.gradle.kts:57` signs release builds with the debug key. Add a `key.properties`-based release signing config (already gitignored) before any Play upload. Also set `allowBackup`/backup rules, network security config and R8 in 1.7 as planned.
3. **CI hardening:** add `persist-credentials: false` to `actions/checkout`, `timeout-minutes` per job, and a coverage-threshold check (the gate requires ≥80%, but CI does not enforce it). Add a CI step that runs `test/qa/bootstrap_qa_test.dart` (or an equivalent) with each example define file, because plain `flutter test` never runs the success path of `bootstrap()`. Consider not cancelling in-progress runs on `main` (`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`).
4. **gitleaks:** on `pull_request` in a private repo, `gitleaks-action` lists PR commits and may post comments through the API. With only `contents: read` this may fail. Check this on the first PR and add `pull-requests: read` to the `secret-scan` job if needed. Organization-owned repos also need a `GITLEAKS_LICENSE` secret.
5. **Placeholder configs:** `sb_publishable_REPLACE_ME` and `https://YOUR-PROD-PROJECT.supabase.co` pass validation. Consider rejecting `REPLACE_ME`/`YOUR-` values for staging and prod in the BUG-2 pre-build script, while CI keeps an explicit opt-out for its example-config builds.
6. **Web CDN:** the default web build fetches CanvasKit from `www.gstatic.com`. For the business and admin portals, and for the plan's offline/slow-network goals, consider `--no-web-resources-cdn`.
7. **iOS flavors:** iOS has one bundle ID and no schemes, so `flutter run --flavor dev` fails on iOS. That is expected ("Android first"), but record it as a task for when iOS starts.
8. **Housekeeping:** `pubspec.yaml` still has template comments (for example the Cupertino Icons note with no dependency under it). `ConfigErrorApp` strings should move to ARB (or be explicitly exempted) in 1.4.
9. Consider moving `test/qa/env_examples_qa_test.dart` into the main test suite, since it guards config drift that CI depends on.
