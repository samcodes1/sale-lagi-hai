### 4.9-N1 (S3): the blocked-notifications note depends on a status Android never reports
- **File:**
  - `lib/features/settings/presentation/notification_settings_screen.dart:37-40` (`_checkPermission`);
  - `:120` (`blocked` only when `permanentlyDenied`);
  - `:166-171` (Open settings, then an immediate re-check).
- **Root cause:**
  - On Android, `Permission.notification.status` returns `denied` for both "never asked" and "permanently denied". See `permission_handler_android` `PermissionManager.java:701-707` ("a status check cannot detect 'permanently denied'") and the platform interface docs. Only `request()` returns `permanentlyDenied`.
  - `openAppSettings()` returns `true` as soon as Settings opens, not when the shopper comes back.
- **Steps (Android 13+):**
  1. Deny notifications twice, or turn them off in system settings.
  2. Signed in, open Settings → Notifications.
- **Expected (SETTINGS.md):**
  - a note says notifications are off for this app, with Open settings;
  - "Coming back re-checks".
- **Actual:**
  1. On entry there is no note (the status is `denied`).
  2. Tapping Push asks, the request returns `permanentlyDenied`, and the note appears.
  3. Tapping Open settings re-checks at once, gets `denied` again, and the note disappears while Settings is still in front.
  4. Nothing re-checks when the app resumes.
  5. If push is On in the account but Android blocks notifications (revoked later), the switch shows **On** with no note. The shopper believes alerts are coming.
- **Workaround:** tap Push again after granting.
- **Evidence:** `test/qa/settings_qa_test.dart`:
  - "QA BUG 4.9-N1: blocked by Android, the note stays while Settings is open" (fails);
  - "QA BUG 4.9-N1: push on in the account while Android blocks notifications shows the note" (fails).

  Both run through permission_handler's method channel, answered as the Android plugin does.
- **Developer test gap:** `settings_screens_test.dart` "blocked in the phone settings" uses a fake whose `status()` returns `permanentlyDenied` and that flips to `granted` before Open settings. Android does neither.
- **Fix:**
  - Remember "blocked" from a `permanentlyDenied` request result, and clear it only when a status check says `granted`.
  - Re-check on `AppLifecycleState.resumed` (an `AppLifecycleListener`), not right after `openSettings()`.
  - Show the note whenever `prefs.pushEnabled` is true and the status is not `granted`.

### 4.9-N2 (S3): a second tap on Push while the system dialog is up turns push on without a grant
- **File:**
  - `notification_settings_screen.dart:55-66` (`_setPush` has no re-entry guard and treats `unavailable` as allowed);
  - `lib/core/device/notification_permission.dart:43-53` (every `PlatformException` becomes `unavailable`).
- **Steps:**
  1. Signed in, push off, permission not yet granted.
  2. Double-tap the Push switch. The dialog takes a moment to appear.
  3. Choose "Don't allow".
- **Expected:** push stays off, and nothing is saved.
- **Actual:**
  1. The second tap calls `request()` while the first is pending.
  2. The Android plugin answers with an error ("A request for permissions is already running", `PermissionManager.requestPermissions`), which is a `PlatformException`.
  3. That maps to `unavailable`, and `_setPush` saves `push_enabled = true`.
  4. The account then has push on while the phone has denied it.

  The same happens with any other `PlatformException` from `request()`, such as "Unable to detect current Android Activity".
- **Evidence:** "QA BUG 4.9-N2: a second tap while the system dialog is up does not turn push on without a grant" fails: `pushEnabled` is `true`, and the server row has `push_enabled = true`.
- **Fix:**
  - Ignore taps while a request is in flight (an `_asking` flag, or disable the switch).
  - In `PlatformNotificationPermission.request`, map a `PlatformException` to `denied`. Keep `unavailable` for `MissingPluginException` only.

### 4.9-N4 (S3): a failed save also undoes a later save that the server kept
- **File:** `lib/features/settings/application/alert_prefs_providers.dart:52` (`before = state.value`) and `:92` (`state = AsyncData(before)`).
- **Steps:**
  1. On a slow connection, turn off "Brands you follow" (A).
  2. While A is in flight, turn off "New deals in your city" (B). B is saved.
  3. A then fails.
- **Expected:** brands back on (A failed); city stays off (B is on the server).
- **Actual:** the whole state goes back to before A, so city shows **On** while the server has it off. The screen and the account disagree until the page is reopened. A later tap on the city switch sends `my_city: false` again, which changes nothing, so the shopper sees it "not work".
- **Evidence:** "QA BUG 4.9-N4: a failed save does not undo a later one that the server kept" fails (`myCity` is `true`). It uses `PrefsServer`, which applies each call as `update_alert_prefs` does.
- **Fix:** on failure, revert only the fields this change sent, onto the current state, or serialize the saves. Alternatively, re-read `my_alert_prefs` after a failure.

### 4.9-N6 (S3): offline, a change is reverted instead of queued
- **File:** `alert_prefs_providers.dart:86-94`. The spec is `docs/ux/UX_ARCHITECTURE.md:70`, S19: Error is "Save failed → revert + toast", and Offline is "**Queued**".
- **Steps:** with the phone offline, change any topic, the frequency or quiet hours.
- **Expected:** the change is kept and sent when the connection returns.
- **Actual:**
  - it reverts with "Couldn't save that. Try again.", the same as a server error;
  - `settings_screens_test.dart` "a failed save comes back as it was, with a note" pins this with `OfflineFailure`.

  Workaround: redo it once online.
- **Fix:** on `OfflineFailure`, keep the optimistic value, queue the changed fields, and flush them when `networkStatusProvider` reports online (with a "Will save when you're online" note). Otherwise, get the UX spec changed and documented.

### 4.9-C1 (S3): a card number typed in Urdu digits passes both checks
- **File:**
  - `lib/core/text/card_numbers.dart:7`: `\d` in a Dart `RegExp` is ASCII only;
  - `supabase/migrations/20261029260000_no_card_numbers.sql:38`: the same pattern, then `regexp_replace('[^0-9]')`.
- **Steps:** in Urdu, Report on a card offer with the note "میرا کارڈ ۴۱۱۱ ۱۱۱۱ ۱۱۱۱ ۱۱۱۱". Gboard's Urdu layout types these digits (U+06F0–06F9).
- **Expected:** the note is refused, as the Western-digit form is (4.7-P1).
- **Actual:** the app sends it, and the database stores it for moderators. Arabic-Indic digits (U+0660–0669) pass too.
- **Evidence:**
  - `test/qa/settings_units_qa_test.dart` "QA BUG 4.9-C1" (fails);
  - `supabase/tests/database/qa_card_numbers_urdu.test.sql` tests 3–4 (`todo`, failing).
- **Fix:** map U+0660–0669, U+06F0–06F9 (and full-width U+FF10–FF19) to 0–9 before matching. In Dart, use a code-unit map. In SQL, use `translate(input, '٠١٢٣٤٥٦٧٨٩۰۱۲۳۴۵۶۷۸۹', '01234567890123456789')`. Do the same in `LogRedactor`.

### 4.9-L1 (S3): the privacy policy's contact route may not exist
- **File:**
  - `assets/legal/privacy_en.txt:26` and `privacy_ur.txt:26`: "Write to us from Settings, About";
  - `lib/app/config/app_config.dart:102-106`: SUPPORT_EMAIL is optional for every flavor;
  - `env/prod.example.json`: `"SUPPORT_EMAIL": ""`.
- **Steps:** build prod from the example env file, then open Settings → About.
- **Expected:** a way to contact us, as the policy promises. Play's User Data policy also expects the privacy policy to give a contact.
- **Actual:** About has no Contact us row (`about_screen.dart:53`), so the policy points to nothing.
- **Fix:** make `AppConfig.fromMap` require SUPPORT_EMAIL when `flavor.isProduction`, and fill it in `prod.example.json` with a placeholder. Or put the address in the policy text itself.

### 4.9-C2 (S4): other separators hide a card number
"4111.1111.1111.1111", "4111  1111  1111  1111" and "4111 - 1111 - 1111 - 1111" pass. The pattern allows a single space or dash between digits (`card_numbers.dart:7`, SQL `:38`). Fix: allow `[\s.\-–]{0,3}` between digits in both. Evidence: "QA BUG 4.9-C2" (skipped; fails unskipped), and `qa_card_numbers_urdu` tests 5–6 (`todo`).

### 4.9-N5 (S4): with no `alert_prefs` row, a change is shown as saved
- **What happens:** `update_alert_prefs` updates `where user_id = auth.uid()` and returns no row when there is none (`qa_settings.test.sql`, the last test). `change()` treats any `Success` as saved (`alert_prefs_providers.dart:89-90`). SETTINGS.md expects missing rows ("With no row, the client uses the defaults"), so every change in that state is silently lost.
- **Fix:** treat an empty result as a failure, or make the RPC upsert.
- **Evidence:** "QA BUG 4.9-N5" (skipped; fails unskipped).

### 4.9-P1 (S4): "Clear everything" leaves the theme in memory
- **What happens:** `privacy_screen.dart:48-59` clears storage and preferences, but `themeModeProvider` keeps "Dark" for the session. The next launch reads no key and shows "As on this phone". Invalidating it isn't enough, because `savedThemeModeProvider` is overridden with the startup value.
- **Fix:** add `ThemeModeController.reset()`, which sets `system` without saving, and call it from the clear.
- **Evidence:** "QA BUG 4.9-P1" (skipped; fails unskipped).
- **Otherwise the clear is complete** (passing QA test):
  - signed out, and the account is not deleted (`deletedIds` is empty);
  - recent searches, saved deals and cards are empty in memory;
  - alert prefs are `null`, the store is empty after settling, and the app returns to the language step.

### 4.9-S1 (S4): the city row says "All Pakistan" when cities can't load
`settings_screen.dart:25,51`: when `citiesProvider` fails (offline, first run), `city` is `null`, so the subtitle claims "All Pakistan" while the shopper's city is Karachi. Fix: use `allPakistan` only when `cityId == null`; otherwise show the cached name or nothing. Evidence: "QA BUG 4.9-S1" (skipped).

### 4.9-M1 (S4): capitals in the SUPPORT_EMAIL domain are refused
`link_service.dart:31` and `app_config.dart:121` end with `\.[a-z]{2,}$`, so `help@SaleLagiHai.PK` fails `AppConfig` and the build stops at the config error screen. Fix: `[A-Za-z]{2,}`, or lower-case the domain first. Evidence: "QA BUG 4.9-M1" (skipped).

### 4.9-T1 (S4): `AlertPrefs.fromRow` accepts out-of-range times
`alert_prefs.dart:40-42` accepts any integer. Postgres `time` stores `24:00:00`, which is reachable through the RPC, and `quiet_start <> quiet_end` allows `00:00` to `24:00`. The result is `TimeOfDay(hour: 24)`, which asserts in debug and shows "12:00 PM" in release. Fix: range-check hour 0–23 and minute 0–59, else use the default. Evidence: "QA BUG 4.9-T1" (skipped).

### 4.9-V1 (S4): 200% text, Urdu app-bar titles and the time picker
- **Urdu app-bar titles:** at 200%, the Nastaliq titles ("نوٹیفکیشنز", "رازداری", "سیٹنگز") are taller than the toolbar and draw over the first list row when it scrolls under. See `docs/qa/screens/4.9/notif-bottom_360x800_dark_ur_ts2.png` and `privacy-bottom_360x800_light_ur_ts2.png`. This is app-wide; 4.5 BUG-3 is related.
- **Time picker:** at 200%, Material's picker clips its AM/PM toggle to "A"/"P" (`quiet-picker_360x800_light_en_ts2.png`, `quiet-picker_360x800_dark_ur_ts2.png`).
- **Fix:**
  - scale `toolbarHeight` with the text scaler (or clamp the title's scale);
  - wrap the picker in `MediaQuery.withClampedTextScaling(maxScaleFactor: 1.5)` through `showTimePicker(builder:)`, or open it in input mode at large text.

## Recommendations (non-blocking)
- The demo gateway's `update_alert_prefs` (`demo_gateway.dart:323-332`) has gaps:
  - it compares `'23:00'` with a stored `'08:00:00'`;
  - it checks only `quiet_start`;
  - it keeps one row for all users.

  `PrefsServer` in `test/qa/settings_qa_test.dart` is a closer model to reuse.
- `PrivacyScreen._clearPhone` ignores the `Result` of `signOut()`. With Supabase the local session is gone anyway, but `GoogleSignIn.signOut()` is skipped when the server call throws (`supabase_auth_repository.dart:108-111`). Run the Google sign-out in a `finally`.
- Style the dialog's "Clear" as destructive (error colour), as on Delete account. "Clear saved copies of deals" uses `Icons.cached`, a sync symbol; `Icons.delete_sweep_outlined` reads better.
- Add the developer's guideline loop for dark mode and a scroll-through at 200% (QA's version passes today) so regressions are caught by the main suite.
- Navigating straight to `/sign-in` by URL (no page to pop back to) raised a page error at the end of sign-in in the web build. This is a QA-driver artefact here, because the app's own button pushes the route. Recheck it when deep links land in 5.3.
- Per-topic Android notification channels and the Ramadan/Jumu'ah rules are deferred, as SETTINGS.md says. Track them in Phase 5.
