## Bugs

### BUG-1 (S2) — `flutter_deeplinking_enabled` is ignored; Flutter deep-link handling is still on
- **Environment:** all flavors and builds (manifest), commit fd29701.
- **Steps:**
  1. Read `android/app/src/main/AndroidManifest.xml:46-49`: the meta-data is a child of `<application>`.
  2. Read how Flutter reads it:
     - `FlutterActivity.shouldHandleDeeplinking()` (`/opt/flutter/engine/src/flutter/shell/platform/android/io/flutter/embedding/android/FlutterActivity.java:1423`) calls `getMetaData()`.
     - `getMetaData()` is `getPackageManager().getActivityInfo(getComponentName(), GET_META_DATA).metaData` (`:1313`), so only the **activity's** meta-data is read.
     - `FlutterActivityLaunchConfigs.deepLinkEnabled` (`:55-62`) returns **true** when the key is missing.
  3. `FlutterActivityAndFragmentDelegate.maybeGetInitialRouteFromIntent` (`:551`) then uses `intent.getData().toString()` as the initial route. `onNewIntent` (`:977`) pushes it with `pushRouteInformation`.
- **Expected:** Flutter ignores intent data, as CHECKLIST.md says ("Flutter deep linking off" ✅), the manifest comment says, and `references/android-hardening.md §1` shows (the meta-data inside `<activity>`).
- **Actual:**
  - Any installed app can start the exported `MainActivity` with an explicit intent and `setData(<any URI>)`. No intent-filter is needed for an explicit intent.
  - go_router then navigates to that location, which bypasses the single validating DeepLinkService the plan requires (Phase 5.3).
  - Today the reachable routes are only `/deal/:id`, `/brand/:slug`, `/category/:slug` and tabs, with validated parameters; the dev routes redirect in prod. So the immediate impact is limited, but the control the sub-phase claims is not in effect.
  - The manifest lint enforces the wrong placement: `test/security/android_config_test.dart:76-81` looks in `application.findElements('meta-data')`, so it passes.
- **Why S2:** it is a core 1.7 deliverable (manifest hardening, "Flutter deep linking off") that is silently not working, and the gate's own lint gives a false pass. It is not S1 only because no sensitive route exists yet.
- **Fix:**
  - Move the `<meta-data android:name="flutter_deeplinking_enabled" android:value="false"/>` inside `<activity android:name=".MainActivity">`.
  - Change the lint to look in the activity's children, and assert there is no application-level copy.
  - Note: the Flutter Gradle plugin's `DeepLinkJsonFromManifestTaskHelper.kt:77-89` also reads the flag per activity.
- **Reproducer:** `test/qa/security_baseline_qa_test.dart`, "BUG-1 … the flag is meta-data of MainActivity". It fails with `QA_KNOWN_BUGS=true`: no meta-data on the activity.

### BUG-2 (S3) — audit_deps ignores every range pub.dev returns (`ECOSYSTEM`), so it relies only on `versions` lists
- **Steps:**
  1. `curl -H 'accept: application/json' https://pub.dev/api/packages/dio/advisories`, and the same for `http`.
  2. Every advisory has `"ranges":[{"type":"ECOSYSTEM", "events":[{"introduced":"0","fixed":null,…},{"introduced":null,"fixed":"5.0.0",…}]}]`.
  3. `tool/audit_deps.dart:148` does `if (range['type'] != 'SEMVER') continue;`.
- **Expected:** ranges are evaluated. OSV ECOSYSTEM ranges for Pub use pub's semver ordering, so the same code applies.
- **Actual:**
  - The range logic (lines 145-169) never runs on real data. Detection only works through the `affected[].versions` enumeration (line 144).
  - That list is a snapshot: an advisory with no fix yet ("introduced" only) misses versions published after it was enumerated, and so does an advisory whose list is empty.
  - The unit tests (`test/tool/audit_deps_test.dart:113-167`) use `SEMVER` fixtures, a shape pub.dev never serves, so they pass. OSV-Scanner in the same job is the compensating control, hence S3.
- **Fix:** accept `type` in `{SEMVER, ECOSYSTEM}`. Sort the events (OSV doesn't require order). Add fixtures copied from the real pub.dev JSON, with null fields.
- **Reproducers:** `test/qa/audit_deps_qa_test.dart`:
  - "an ECOSYSTEM range is evaluated without a versions list" (dio 4.0.6 should be reported; got `[]`);
  - "an open ECOSYSTEM range (no fix yet) affects later versions".
  - A passing guard confirms the `versions` path still works on real data.

### BUG-3 (S3) — the source-hygiene test misses common cleartext and console-logging forms
- **File:** `test/security/source_hygiene_test.dart:30-33` (comment stripping), `:56` (console), `:64` (cleartext).
- **Bypasses that pass today** (each is its own reproducer; patterns are extracted live from the hygiene test):
  - `Uri.http('api.x.pk')`
  - `Uri(scheme: 'http', …)`
  - `'HTTP://…'` (the regex is case-sensitive; `Uri` lower-cases the scheme)
  - `'http:' '//…'` (adjacent literals)
  - `'http://localhost.attacker.example'` (the negative lookahead allows any host that *starts with* localhost, 127.0.0.1 or 10.0.2.2)
  - `'ws://…'` (cleartext WebSocket)
  - `debugPrintSynchronously(…)` and `debugPrintThrottled(…)` (`\bdebugPrint\b` doesn't match them)
  - `developer.log(…)` (`dart:developer`)
  - Any code after a string holding ` //` on the same line, e.g. `final a = ' //'; print(token);`. The comment regex `\s//.*$` deletes the rest of the line.
- **Also:**
  - All `.xml` files are excluded from the cleartext check, to skip `xmlns`, so an `http://` URL in Android resources is never checked.
  - `web/` is not scanned at all.
- **Expected:** the hygiene test catches the usual ways of writing a cleartext URL or console output.
- **Actual:**
  - None of these is caught. No such pattern exists in `lib/` today (grep is clean).
  - `AppConfig` still enforces `https://` for the Supabase URL, hence S3.
- **Fix:**
  - Use a case-insensitive `(?:http|ws)://` with a host-anchored allowlist: `(?!(?:localhost|127\.0\.0\.1|10\.0\.2\.2)(?:[:/'"]|$))`.
  - Ban `Uri.http(`, `scheme: 'http'`, `debugPrint\w*`, `dart:developer` and `console.`.
  - Strip comments with a tokenizer-aware rule, or only whole-line `//` comments.
  - Skip only `xmlns:` attributes instead of whole `.xml` files.
- **Reproducers:** `test/qa/security_baseline_qa_test.dart`, group "BUG-3" (11 tests, plus a positive control that passes).

### BUG-4 (S3) — a keystore password hard-coded in a Gradle script is not detected
- **File:** `.gitleaks.toml:35`; `test/security/source_hygiene_test.dart:22`.
- **Steps:** apply rule `android-signing-password` to `storePassword = "<pw>"` (Kotlin DSL), `keyPassword '<pw>'` (Groovy) and `keyPassword = "<pw>"`, with a password of 6+ characters in place of `<pw>`. (Round 3: placeholders, so this report doesn't trip the rule itself.)
- **Expected:** reported. `android/app/build.gradle.kts` is exactly where signing is configured, and this is the likeliest way a password leaks.
- **Actual:**
  - Nothing is reported, because the value class `[^\s$()"']` excludes quotes. The rule only catches the unquoted `key.properties` form.
  - The default `generic-api-key` rule needs entropy ≥3.5 and `[\w.=-]` values, so it misses typical passwords (`hunter2hunter2` has entropy 2.8, and `!` is not in the class).
  - The hygiene test's `(store|key)Password` pattern never sees build scripts: it scans `android/app/src` only.
- **Fix:** add a second alternative for the quoted DSL form:
  ```
  (?:store|key)Password\s*(?:=\s*)?["']([^"'$]{6,})["']
  ```
  It excludes `$` so `"$envVar"` doesn't match.
- **Reproducers:** group "gitleaks rules", "a hard-coded Gradle signing password is caught: …" (3 tests). A positive-control test confirms the regexes are loaded from `.gitleaks.toml`.

### BUG-5 (S4) — `[[allowlists]]` is silently ignored by the gitleaks version CI installs
- **File:** `.gitleaks.toml:41`; `.github/workflows/ci.yml:32-34`.
- **Steps:**
  1. gitleaks-action `e0c47f4` (v3.0.0), `src/index.js:138`: `process.env.GITLEAKS_VERSION || "8.24.3"`.
  2. gitleaks v8.24.3 `config/config.go:44-50` reads only a top-level `Allowlist` (`[allowlist]`).
  3. Top-level `[[allowlists]]` arrived in v8.25.0 (`config.go:51-52`). Viper drops unknown keys.
- **Expected:** the allowlist applies.
- **Actual:**
  - It is dead config.
  - No harm today: my emulation of the v8.24.3 `jwt` rule doesn't match either fixture anyway. The first fixture's signature is 8 characters, under the 10-character minimum; the second has no signature.
  - It will mislead whoever relies on it next.
- **Fix:**
  - Set `env: GITLEAKS_VERSION: 8.x.y` (≥ 8.25.0, pinned) on the gitleaks step. That also pins the scanner explicitly.
  - Or use the singular `[allowlist]` table.
- **Reproducer:** "the allowlist syntax matches the gitleaks version CI runs".

### BUG-7 (S4) — documentation and comment inaccuracies
1. `docs/security/CHECKLIST.md:58` says the cleartext ban covers "plugins, **Custom Tabs** and image loaders on the platform stack".
   - Custom Tabs render in the browser's process; the app's network security config does not apply to them.

   - **Fix:** reword the comment ("a release workflow that sets REQUIRE_RELEASE_SIGNING=true fails") and rename the test.
4. `.github/dependabot.yml:1` says "Security updates are opened as soon as an advisory is published".

## Recommendations (non-blocking)
- **Check the merged manifest in CI.** In `build-android-release`, check the merged manifest (`build/app/intermediates/merged_manifests/prodRelease/**/AndroidManifest.xml`, or `apkanalyzer manifest print`) for:
  - `exported="true"` on anything other than MainActivity (if AndroidX's `ProfileInstallReceiver` shows up, it is exported but DUMP-protected, so allowlist it explicitly);
  - `debuggable`;
  - the permission list.
  - Today this is a manual step.
- **Schedule the audit.** Add `schedule:` (e.g. weekly) to the workflow for `dependency-audit`. Today a new advisory against an unchanged lockfile is only noticed on the next push or PR. Also give jobs `timeout-minutes`.
- **Test the online path.** Make `audit_deps.dart`'s base URL and `HttpClient` injectable and unit-test the online path with a local `HttpServer` (`tool/` is outside the coverage gate today). Fetch concurrently with a small pool: today it takes 75 s for 232 sequential requests.
- **Pin the OSV image digest.** The osv-scanner action pulls `ghcr.io/google/osv-scanner-action:v2.7.0` by tag. The SHA pin on the action does not pin the image, so consider the reusable workflow or a digest pin. Consider SARIF upload so results show under Security → Code scanning.
- **Exclude secure-storage config files.** For consistency, also exclude `FlutterSecureStorageConfiguration.xml` and `FlutterSecureStorageConfiguration:FlutterSecureStorage.xml` from backups. Today they are harmless (markers only).
- **Phase 4 storage defaults.** supabase_flutter's default session storage and PKCE verifier storage are SharedPreferences, which these rules back up. Make sure Phase 4 wires the session (and the code verifier) into `SecureStore`, as CHECKLIST STORAGE-1 says.
- **Move the signing check out of configuration time.** `build.gradle.kts`: the `REQUIRE_RELEASE_SIGNING` `throw` runs at configuration time, so with the variable set even `assembleDebug` fails. A missing `storeFile` in `key.properties` also throws an NPE (`file(null)`). Consider validating inside `gradle.taskGraph.whenReady`, or only for release tasks.
- **Group Dependabot's Gradle updates with Flutter's.** Dependabot `gradle` will propose AGP, Kotlin and wrapper bumps beyond what Flutter 3.47.8 supports. Consider ignoring major and minor AGP/Kotlin updates and bumping them together with Flutter.
- **Catch service_role JWTs under any name.** Add a gitleaks rule for a JWT whose payload base64 contains `c2VydmljZV9yb2xl` (base64 of `service_role`). Today the custom rule needs a `service_role` name near the value; the default `jwt` rule still catches it, but without the specific label.

### R2-1 (S4) — the hygiene test still misses some cleartext and console forms
