### The accepted trade-offs
- **BUG-14, 13-digit numbers starting 1–7 are redacted as CNICs: agreed, reasonable.**
  - A CNIC without dashes is indistinguishable from such a number, and a CNIC is national-ID PII. Failing safe is the right call.
  - The cost: epoch-millisecond timestamps (all of them until 2033) and EAN-13 barcodes of imported goods are hidden. For example, China `690…` and Germany `40…` become `[cnic]`. Pakistani `896…` barcodes are kept.
  - The workaround (log ISO times or `DateTime`, never raw epochs) is cheap. Consider adding it to the logger's doc comment.
- **BUG-15, debug builds keep `FlutterError.presentError`: agreed, reasonable.**
  - Debug builds don't ship. The rich widget-error output is the main debugging tool, and release builds were verified not to present (`logger_guard_qa_test.dart`).
  - One condition: tester builds handed out through Play internal testing or Firebase App Distribution must be release-mode builds of the dev/staging flavors, never debug APKs. Note it in the 1.7 release checklist.

#### BUG-18 (S3): Keyed secrets in camelCase, prefixed or escaped form still leak
- **File:** `lib/core/logging/log_redactor.dart:116-122`. The key must be one of a fixed list of snake_case names, and `(?<![\w])` rejects any key with a prefix (`refreshToken`, `fcmToken`, `client_secret`, `X-Api-Key`). The quote group `["']?` does not allow `\"`.
- **Steps / actual:** these come back unchanged:
  - `Session(accessToken: opaque123, refreshToken: abc456)`
  - `refreshToken: v1.abc123`
  - `fcmToken=dXyZ123abc`
  - `otpCode: 482913`
  - `X-Api-Key: abc123`, `api-key: abc123`
  - `client_secret=abc123`, `secret_key=abc123`
  - `set-cookie: session=abc123`
  - `{\"refresh_token\":\"abc123\"}`
- **Expected:** the values are hidden. `freezed` (the project's model library) generates exactly `Class(field: value, …)` for `toString()`, so a session or token model that reaches `logger.error(error: …)` or a message leaks. A JWT access token is still caught by the `eyJ` rule; opaque refresh tokens and FCM/OTP values are not.
- **Evidence:** 11 reproducers in group "BUG-18".
- **Severity rationale:** as in round 1, nothing logs these today. This is the remaining gap of BUG-3 and becomes S1 in Phase 2.
- **Suggested fix:** match a generic key, `(?<![\w-])([A-Za-z][\w-]{0,40})(\\?["']?\s*[:=]\s*\\?["']?)([^\s"'\\&,;)}\]]{1,512})`, and redact the value only when `isSensitiveKey(m[1])`. `isSensitiveKey` already handles camelCase, acronyms and fragments. Keep the URL-only `code` handling from BUG-21.

#### BUG-19 (S3): Keyed coordinates with quoted values or prefixed keys leak
- **File:** `lib/core/logging/log_redactor.dart:125-129`. `(?<![\w])` rejects `userLat` and `user_lat`, and the value must start right after `[:=]?\s*`, so a quote before the number fails.
- **Steps / actual:** these come back unchanged:
  - `{"lat": "24.8607", "lng": "67.0011"}` (string-typed JSON coordinates are common in APIs)
  - `userLat: 24.8607, userLng: 67.0011`
  - `user_lat=24.8607&user_lng=67.0011`
  - `deviceLatitude=24.8607`
  - `latitude%3D24.8607`
- **Expected:** they are redacted (secure-dev §8: lat/lng with more than 2 decimals).
- **Evidence:** 5 reproducers in group "BUG-19".
- **Suggested fix:** use the same generic-key approach as BUG-18, with a key predicate (`lat|lng|lon|latitude|longitude` as the last camel/snake word), allow `\\?["']?` around the value, and decode `%3D`/`%3A` before matching.

#### BUG-20 (S3): Secure storage can't recover from a key mismatch with `resetOnError: false`
- **File:** `lib/core/storage/secure_store.dart:255-257` (`AndroidOptions(resetOnError: false)`) and `:262-268` (`read` returns `null` and does nothing else).
- **Cause (flutter_secure_storage 11.2.0 Android source):**
  - Every method call, including `deleteAll`, first runs `secureStorage.initialize(...)` (`FlutterSecureStoragePlugin.java:176-178`); only `checkUpgradeStatus` skips it.
  - After a restore to a new phone (or OEM Keystore loss), unwrapping the stored data key throws `BadPaddingException`/`InvalidKeyException` (`FlutterSecureStorage.java:421-426`), which goes to `handleKeyMismatch` (`:1016-1068`).
  - Migration can't help, because the old key is gone. With `resetOnError` false the plugin answers `onError` ("Enable resetOnError=true or call deleteAll()"), and `preferences` stays `null`, so the next call fails the same way.
  - `deleteAll()` from Dart also fails, because it goes through `initialize()` too.
- **Steps (mimicked over the real method channel, `round2_qa_test.dart` group "BUG-20"):**
  1. Key mismatch after restore.
  2. `read(authSession)` → `null` (signed out, correct).
  3. The user signs in again, so `write(authSession, 'new-session')`.
- **Expected:** the new session is saved. Secure-dev §4 says "treat empty as signed-out, never as an error".
- **Actual:**
  - `write` throws `StorageFailure` on every launch, forever.
  - The user must do an OTP sign-in (an SMS cost) every time the app starts, until they clear the app data or reinstall.
  - Nothing is logged, so this is invisible in crash reporting.
  - In round 1 the session was wiped once; now storage is broken permanently.
- **Severity rationale:** latent, because there is no `SecureStore` consumer yet and the 1.7 backup rules will remove the most common trigger (restore). It becomes S2 once Phase 2 stores the session.
- **Suggested fix:** keep `resetOnError: false` for normal calls, so transient errors don't wipe data. On a `PlatformException` from `read`:
  1. Log a warning with `e.code` only.
  2. Run one recovery call, `FlutterSecureStorage(aOptions: AndroidOptions(resetOnError: true)).deleteAll()`. The plugin caches the instance per prefs name, but `initialize()` adopts the config passed on each call (`FlutterSecureStorage.java:249-254`), so this call can reset the data and keys.
  3. Return `null`.

  Do the same once in `write` before throwing `StorageFailure`. Verify on a device in 1.7, with the restore test from checklist B2. The round-1 BUG-7 tests and this one must all pass.

#### BUG-21 (S3): Database error codes are redacted as if they were OAuth codes
- **File:** `lib/core/logging/log_redactor.dart:118` (`code` in the keyed-secret list).
- **Steps / actual:**
  - `PostgrestException(message: new row violates row-level security, code: 42501, details: null)` → `code: [redacted]`.
  - `error code=PGRST116` → `code=[redacted]`.
  - `code: 23505` → `code: [redacted]`.
- **Expected:** Postgres and PostgREST error codes are kept. They are the main evidence for RLS denials (42501), unique violations (23505) and "no rows" (PGRST116), exactly what Phase 2 debugging and the RLS work need. The OAuth/PKCE `code` in the login-callback URL must stay hidden (that test passes today).
- **Severity rationale:** wrong behaviour with a workaround (map Postgrest errors to typed failures before logging). It was introduced by the BUG-3 fix.
- **Suggested fix:** treat `code` as secret only in URL query or fragment context (`[?&#]code=`), or when the value is ≥ 16 characters (Supabase PKCE codes are UUIDs).

#### BUG-22 (S4): Remaining phone layouts
- **File:** `log_redactor.dart:168-179`.
- **Actual:** these are unchanged:
  - `3001234567`: the national number without the trunk 0. UX S20 says "+92 prefilled"; if that is a separate prefix chip, this is exactly the field value.
  - `0300–1234567` (en dash)
  - `0300 - 123 - 4567` (only the first separator allows 3 characters)
  - `0300\u200B1234567` (zero-width space)
  - `０３００１２３４５６７` (fullwidth)
- **Suggested fix:**
  - Also match `(?<!\d)3[0-4]\d[\s.\-]?\d{7}(?!\d)` (Pakistani mobile ranges 30x–34x).
  - Allow `[\s.\-–—()]{0,3}` at every separator.
  - Strip `\u200B-\u200F\u2066-\u2069` and map fullwidth digits in `_normalizeDigits`.
- **Evidence:** group "BUG-22".

#### BUG-23 (S4): Other small redactor gaps
- **File:** `log_redactor.dart` (email `:154-160`, card `:183-186`, JWT `:135`, truncation `:217-221`, key words `:20-83`).
- **Actual:**
  - `email=ali%40gmail.com` is not redacted.
  - `card-4111111111111111` and `4111-1111-1111-1111-` are not redacted (the `(?<![\d-])`/`(?![\d-])` guards).
  - A JWT without its signature, `eyJ….eyJ…`, is not redacted. Neither is a JWT cut by the 8 KB truncation: the output ends `…eyJwaG9uZSI6IjkyMzA…[truncated]`, which is base64 of `{"phone":"9230`.
  - The keys `refresh`, `oauthCode`, `cvc`, `dob` and `signature` are not sensitive.
- **Suggested fix:**
  - Decode `%40` before the email rule.
  - Use `(?<!\d)`/`(?!\d)` for cards.
  - Make the JWT signature optional (`(?:\.[\w-]{0,4096})?`).
  - Truncate *after* redacting a slightly longer prefix (e.g. redact the first `maxLength + 512` characters, then cut at `maxLength`), or drop a trailing partial token at the cut.
  - Add the missing words.
- **Evidence:** group "BUG-23" (10 reproducers).

#### BUG-24 (S4): A cyclic context value crashes the logger
- **File:** `log_redactor.dart:236-243` (`_mask` recurses with no depth or visited set).
- **Steps:** `final m = <String, Object?>{}; m['self'] = m; logger.info('x', context: {'m': m});`
- **Expected:** the record is logged. Dart's own `Map.toString` prints `{...}` for cycles.
- **Actual:** `StackOverflowError` escapes `AppLogger.log` (the call is outside the sink `try`). A 1 M-element list is fine: 206 ms, then capped.
- **Suggested fix:** pass a depth limit (e.g. 8) and an identity `Set` of visited containers to `_mask`, returning `'[cycle]'` or `'[too deep]'`.
- **Evidence:** "BUG-24 (S4): a cyclic context value does not crash the logger".

### Round 2 recommendations (non-blocking)
1. Anchor the JWT rule, `(?<![\w-])eyJ…`, so a run like `eyJeyJeyJ…` has one start position instead of 2,700. That is today's worst case (177 ms on desktop JIT; likely several times slower in AOT on a low-end phone).
2. `mapError` now swallows a mapper's own exception silently (`guard.dart:57-59`). Log it at `warning` (the mapper is buggy), so it doesn't hide.
3. `JsonCache.clear()` lets store errors escape raw, while `put()` wraps them in `StorageFailure`. Wrap them the same way for consistency.
4. Round-1 recommendations 2–6 still stand (stack-trace scrubbing in the 8.4 Sentry reporter, the CI grep for direct storage/logging APIs, the backup restore test in 1.7, the size of the `JsonCache` store, and `kDebugMode` vs `kReleaseMode` for profile builds).

### BUG-1 (S3): The redactor misses common Pakistani phone formats
- **File:** `lib/core/logging/log_redactor.dart:63`. The phone rule `(?:\+92|0092|\b0)[ -]?3\d{2}[ -]?\d{7}\b` allows one separator, and only after the prefix and after the 3-digit network code.
- **Steps:** `LogRedactor().redact(x)` for each input below.
- **Expected:** the subscriber digits are removed (secure-dev rule 8 and §8; CLAUDE.md "Never log personal data").
- **Actual:** these come back unchanged:
  - `923001234567`: E.164 without `+`, which is how Supabase Auth stores `user.phone`. It is 12 digits, so the card rule (13+) misses it too.
  - `92 300 1234567`, `0300-123-4567`, `0300 123 4567`, `+92-300-123-4567`, `+92(300)1234567`, `+92 (300) 1234567`, `0300.1234567`.
  - `phone=%2B923001234567` (URL-encoded `+`).
  - `03001234567abc` (no trailing word boundary).
- **Evidence:** `test/qa/log_redactor_qa_test.dart`, group "BUG-1" (9 reproducers, all fail with `QA_KNOWN_BUGS=true`).
- **Severity rationale:** this is a safety-net gap. No current code path logs a phone number, and release builds have no console sink and a no-op crash reporter, so nothing leaks today. It becomes S1 ("PII in logs") once auth (Phase 2) or Sentry (8.4) lands.
- **Suggested fix:**
  - Normalise first: strip `[\s().-]` between digits, and decode `%2B`.
  - Then match `(?:\+?92|0092|0)?3\d{9}` with no word boundary requirement on the left, or simply redact any run of 10+ digits (with separators) that starts with `3`, `03`, `92` or `+92`.

### BUG-2 (S3): No rule matches Urdu or Arabic-Indic digits

### BUG-5 (S3): Precise coordinates are only redacted in the `lat, lng` comma form
- **File:** `lib/core/logging/log_redactor.dart:65`.
- **Steps:** redact `lat=24.8607&lng=67.0011`, `{"lat":24.8607,"lng":67.0011}`, `at 24.8607 67.0011`, `24.8607;67.0011`, `lat 24.86073`.
- **Expected:** they are redacted. Secure-dev §8 says "lat/lng with more than 2 decimals", and query strings and JSON are the common ways coordinates reach an error message.
- **Actual:** unchanged. `LatLng(24.8607, 67.0011)`, `@24.8607,67.0011,15z` and `-33.865,151.209` *are* redacted, and those cases are kept as regression tests.

### BUG-6 (S3): Redaction is quadratic on long word runs and can freeze the UI
- **File:** `lib/core/logging/log_redactor.dart:57`, the email rule `[\w.+-]+@…`. On a long run of `[\w.+-]` with no `@`, every start position rescans to the end.
- **Steps:** time `redact()` on `'a' * n`. Each rule was measured on its own as well.
- **Actual (JIT, this container):**
  - 1 k chars: 8 ms. 10 k: 760 ms. 20 k: 3.1 s. 40 k: 12.7 s.
  - The email rule alone accounts for all of it; every other rule takes 0 ms.
  - Realistic payloads: a 20 kB base64url blob takes 3.1 s, and an 8 kB signed URL takes 0.49 s. Ordinary prose or HTML is fine (1–2 ms).
  - `log()` runs synchronously on the caller's isolate, and for framework and uncaught errors that is the UI isolate. More than 5 s means an Android ANR.
- **Expected:** linear time. A log call never blocks for more than a few ms.
- **Evidence:** `test/qa/log_redactor_qa_test.dart`, "a 20 kB base64url blob redacts in under 200 ms" (a reproducer) and "ordinary prose of 18 kB redacts fast" (passes).
- **Suggested fix:**
  - Bound the quantifiers: `[\w.+-]{1,64}@[\w-]{1,63}(?:\.[\w-]{1,63}){1,8}`.
  - Truncate `message` and `errorText` to e.g. 4 kB *before* redacting (Sentry truncates anyway).
  - Re-check the other rules with the same 40 k inputs.

### BUG-7 (S3): The secure store wipes everything and returns a sentinel string on any Android error
- **File:** `lib/core/storage/secure_store.dart:37` (`const FlutterSecureStorage()` with default `AndroidOptions`) and `:41-47` (read).
- **Cause:**
  - In flutter_secure_storage 11.2.0, `AndroidOptions.resetOnError` defaults to `true` (`lib/options/android_options.dart:51`).
  - With it on, the Android plugin catches **any** `Throwable` from **any** call, runs `deleteAll()`, and answers `result.success("Data has been reset")` (`android/.../FlutterSecureStoragePlugin.java:271-284`).
  - So the `on PlatformException` branches in the wrapper almost never fire.
- **Steps (simulated over the real method channel, as the plugin answers):**
  1. With the Keystore key unusable (restore to a new phone, the exact case the wrapper's doc names, or a transient Keystore error), call `FlutterSecureStore().read(SecureKey.authSession)`.
  2. Call `FlutterSecureStore().write(SecureKey.authSession, 'session')`.
- **Expected:** `read` returns `null`, so the user is signed out (secure-dev §4, "treat empty as signed-out"). `write` throws `StorageFailure`, as its doc says.
- **Actual:**
  - `read` returns `'Data has been reset'`, a non-null garbage "session".
  - `write` completes normally even though nothing was saved and all other secure data was wiped.
  - A transient error also deletes a valid session (forced re-OTP, which costs an SMS).
  - None of this is logged.
- **Evidence:** `test/qa/storage_qa_test.dart`, "BUG-7: an unreadable value reads as null, not the plugin sentinel" (`Expected: <null> Actual: 'Data has been reset'`) and "BUG-7: a write that fails is reported as StorageFailure".
- **Severity rationale:** there is no consumer of `SecureStore` in 1.2. It becomes S2 (session lost or corrupt on restore) when Phase 2 stores the Supabase session.
- **Suggested fix:**
  - Pass `AndroidOptions(resetOnError: false)` and handle failures in the wrapper. On `read` `PlatformException`, log a warning with `e.code` only (no value), `delete` that key, and return `null`. Keep `write` throwing `StorageFailure`.
  - Alternatively, keep `resetOnError` but treat the sentinel `'Data has been reset'` as `null` in `read` and as a `StorageFailure` in `write`.
  - Device-test the restore case in 1.7 together with the backup rules.

### BUG-8 (S3): The retry policy retries dependents, which Riverpod deliberately does not
- **File:** `lib/core/state/retry_policy.dart:15`, `final cause = error is ProviderException ? error.exception : error;`.
- **Background:**
  - Riverpod 3.4.3's `ProviderContainer.defaultRetry` returns `null` for `ProviderException` (`provider_container.dart:991`). Its docs say this "avoids retrying a provider that isn't the source of the problem" (`stack_trace.dart:35`).
  - Awaiting `.future` gives the raw error, which was verified, so `guard` and `.future` chains are unaffected.
  - A `ProviderException` arises from sync reads and `requireValue` of a failed dependency.
- **Steps:** source `A` always throws `OfflineFailure`. Dependent `B` does `ref.watch(a).requireValue`. Both use `appRetryPolicy` with delays scaled 1/50.
- **Expected:** `B` shows the error as soon as `A` gives up (as with the default policy), and `B` does not retry.
- **Actual:** A gives up at 102 ms scaled (5.1 s real). B gives up at 180 ms (9.0 s real), so the user sees the spinner ~3.9 s longer for each dependency level. B also rebuilt 11 times instead of 2, which multiplies any I/O that B does before reading A.
- **Evidence:** `test/qa/retry_policy_qa_test.dart`, the two "BUG-8" tests (`appRetryPolicy(0, ProviderException(Offline))` = `0:00:00.500000`, expected `null`; delay gap `72` ms scaled, expected `< 20`).
- **Suggested fix:** `if (error is ProviderException) return null;` (as Riverpod does), then apply the `AppFailure` rules to `error` directly. Fix the misleading product test (see test-quality findings).

### BUG-9 (S3): The server's `retryAfter` is uncapped and unvalidated
- **File:** `lib/core/state/retry_policy.dart:18-19`.
- **Steps:**
  - `appRetryPolicy(0, RateLimitedFailure(retryAfter: Duration(hours: 1)))`.
  - The same with `Duration(seconds: -5)`.
- **Expected:**
  - A long wait isn't spent silently in `AsyncLoading(retrying: true)`. Above a cap (e.g. 30 s), return `null` so the UI can show "too many requests, try again in …".
  - Negative values are clamped to zero.
- **Actual:** it returns `1:00:00` and `-0:00:05`.
- **Evidence:** `test/qa/retry_policy_qa_test.dart`, the two "BUG-9" tests.
- **Suggested fix:** `final wait = cause.retryAfter!; if (wait > maxAutoRetryWait) return null; return wait.isNegative ? Duration.zero : wait;`.

### BUG-10 (S3): The cache treats an entry saved "in the future" as fresh
- **File:** `lib/core/storage/json_cache.dart:68` (`entry.ageAt(_clock()) > maxAge`; a negative age is never greater).
- **Steps:**
  1. With the device clock a month ahead, `put('feed', …)`.
  2. Correct the clock.
  3. `get('feed', maxAge: 30 min)`.
- **Expected:** a miss. Phone clocks are set by hand often enough, and NITZ glitches happen too.
- **Actual:** the entry is returned as fresh until the wall clock catches up (a month), so expired deals are served as current.
- **Evidence:** `test/qa/storage_qa_test.dart`, "BUG-10: an entry saved in the future…".
- **Suggested fix:** treat `age < -tolerance` (e.g. 5 min) as stale, or as corrupt and delete it.

### BUG-11 (S3): In debug, uncaught async errors are invisible in the terminal
- **Files:** `lib/core/errors/error_handlers.dart:27-30` (`return true` suppresses the engine's own print) and `lib/core/logging/log_sinks.dart:16` (`developer.log` is the only console output).
- **Steps:**
  1. Run `dart run` on a file that calls `developer.log('HELLO…')` and `print('print-works')`. Only `print-works` appears.
  2. `grep` flutter_tools for a `Logging` stream subscription: there is none, only `Stdout`.
- **Expected:** a developer using `flutter run` or `adb logcat` sees uncaught errors in debug builds.
- **Actual:** uncaught async errors are logged only to the VM service `Logging` stream (IDE debug console and DevTools). In a terminal or CI agent session they vanish. Framework errors are still shown via `presentError` (BUG-15).
- **Severity rationale:** wrong behaviour with a workaround (open DevTools or an IDE). It especially hurts the CLI-driven agents that build this project.
- **Suggested fix:** in debug, let `ConsoleLogSink` also `debugPrint` a one-line summary (it is already redacted), or return `false` from `onError` when `!isReleaseMode`.

### BUG-12 (S4): A throwing `toString()` or mapper escapes the logger and `guard()`
- **Files:** `lib/core/logging/app_logger.dart:104,106` (`'$error'` and `'$value'` run outside any `try`) and `lib/core/result/guard.dart:31,51` (mapper calls are unguarded).
- **Steps:**
  - `logger.error('x', error: objWithThrowingToString)` throws `StateError`.
  - `guard(() async => throw objWithThrowingToString, logger: logger)` throws instead of returning `Failure`.
  - `guard(..., mappers: [(_, _) => throw ArgumentError()])` throws.
- **Expected:** logging never throws, and `guard` always returns a `Result` (its doc: "converts any thrown error into a Failure").
- **Evidence:** `test/qa/logger_guard_qa_test.dart`, the three "BUG-12" tests.
- **Suggested fix:** compute `errorText` and context strings inside `try`, falling back to `'<unprintable ${error.runtimeType}>'`. In `mapError`, wrap each mapper call in `try`/`catch` and treat a throw as `null`, logging it.

### BUG-13 (S4): `guard()` swallows unmapped errors when no logger is passed
- **File:** `lib/core/result/guard.dart:24,33` (`AppLogger? logger` defaults to `null`; `logger?.error`).
- **Expected:** "anything still unrecognised becomes an UnexpectedFailure and is logged" (doc comment, lines 16–19).
- **Actual:** with no logger it is silently converted, so a forgotten argument hides bugs. Three of the product guard tests call `guard` without a logger.
- **Suggested fix:** make `logger` required, or default it to a global or `ref`-provided logger.

### BUG-14 (S4): Ordinary numbers and keys are over-redacted
- **File:** `lib/core/logging/log_redactor.dart:57,61,65` and the word list at `:11-39`.
- **Actual:**
  - `savedAt 1761739200000` → `[card]` (epoch ms is 13 digits).
  - `sku 8964000123456` → `[card]` (EAN-13).
  - `00000000-0000-4000-8000-000000000000` → `[card]-[card]`.
  - `Rs 1.299, 2.499` → `[location]`.
  - `icon@2x.png` → `[email]`.
  - The keys `cardName`, `myCards…`, `sessionCount`, `keyCount` and `locationCity` are hidden, although "my cards" are bank *product* names (threat model §0).
  - UUIDs with hex letters, prices with commas, dates and ratings are fine: 500 random UUIDs were checked.
- **Severity rationale:** this fails safe and only costs debuggability.
- **Suggested fix:**
  - Apply a Luhn check before `[card]`.
  - Require a TLD of 2+ letters, not a file extension, for `[email]`.
  - Consider exact-word matching for `card`/`key`/`session` only when paired with `number`/`token`/`id` respectively.
- **Evidence:** `test/qa/log_redactor_qa_test.dart`, group "BUG-14".

### BUG-15 (S4): Debug builds print the raw exception
- **File:** `lib/core/errors/error_handlers.dart:24` (`FlutterError.presentError(details)` in debug).
- **Expected:** secure-dev rule 8 says "No phone numbers … in **any** build".
- **Actual:** in debug, framework errors are printed unredacted to the console and logcat. This only happens on dev devices with test data, so it is a deliberate trade-off that should be documented or redacted.
- **Suggested fix:** present a copy of `details` whose `exception` is replaced by its redacted text, or accept the trade-off and document it in the skill.

### BUG-16 (S4): The config-error path bypasses the error handlers
- **File:** `lib/app/bootstrap.dart:24-25` (returns before `:31`, `installErrorHandlers`).
- **Actual:** a misconfigured build shows `ConfigErrorApp` with Flutter's default handlers. In release, `dumpErrorToConsole` prints the exception and stack to logcat. The config failure itself is never logged or reported, so a broken release can't be seen in crash reporting once Sentry exists. Errors between `ensureInitialized` and `:31` take the same path.
- **Suggested fix:** create the logger and call `installErrorHandlers` first, then validate the config, and log `AppConfigException` with the *problem codes* only (no values).

### BUG-17 (S4): `JsonCache` housekeeping
- **File:** `lib/core/storage/json_cache.dart:55-57`, `:37-44`.
- **Actual:**
  1. Entries with another `formatVersion` are returned as a miss but never deleted, so they stay forever.
  2. There is no `JsonCache.clear()`. Secure-dev §4 says to "clear [the cache] on sign-out and on account deletion", and `KeyValueStore.clear()` would also wipe settings.
  3. `put()` is expression-bodied, so a non-encodable value throws **synchronously**, and storage errors (e.g. web `QuotaExceededError`) escape raw instead of as `StorageFailure`.
- **Evidence:** `test/qa/storage_qa_test.dart`, "BUG-17 (S4): entries from an old format version are deleted" and "data that is not JSON-encodable is rejected by put()" (this one passes, and documents the sync throw).
- **Suggested fix:** `remove(key)` on a version mismatch. Add `clear()`, which removes `cache.*` keys only. Make `put` `async` and map store errors to `StorageFailure`.

## Recommendations (non-blocking)
1. Fix BUG-1–7 now, while the code is fresh. They are small and well-tested by the reproducers. Otherwise they *must* be closed before Phase 2 (auth, session) and 8.4 (Sentry); see the verdict condition.
2. In the 8.4 Sentry `CrashReporter`, run the stack trace through a scrubber too. Today `LogRecord.stackTrace` reaches sinks unredacted (`app_logger.dart:107`, `log_sinks.dart:25,49`). Dart frames don't contain argument values, but `StackTrace.fromString` and platform-channel traces can carry text.
3. Add a CI grep, or a custom lint, that fails on `FlutterSecureStorage(`, `SharedPreferences` or `developer.log` outside `lib/core/storage` and `lib/core/logging`. Today the `SecureKey` closed list is enforced only by convention. Note that the skill's §4 example (`SecureSessionStorage` using `FlutterSecureStorage` directly with key `sb_session`) bypasses `SecureStore`. Route it through `SecureKey.authSession` in Phase 2.
4. When 1.7 adds backup rules, run the "restore to a new device" test from checklist B2. It is the trigger for BUG-7.
5. `JsonCache` on `SharedPreferencesAsync` loads whole values into memory. That is fine for small feeds; keep large or paginated deal caches for the planned drift/sqflite store.
6. Profile builds (`kReleaseMode == false`) get the debug logger (`minLevel: debug` plus the console sink). If profile builds are given to testers, consider `kDebugMode` instead.
