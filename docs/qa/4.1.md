### BUG-1 (S2): A transient storage read failure wipes a returning shopper's choices
- **Area / file:** `lib/app/bootstrap.dart:108-123`. `loadStartupSettings` reads the locale and the preferences in **one** `try`. Any read error returns `(store: null, locale: null, preferences: const ShopperPreferences())`. `bootstrap.dart:71-74` then leaves `keyValueStoreProvider` at its default, which is the **same** SharedPreferences.
- **Why it loses data:** `PreferencesController` (`preferences_controller.dart:32-39`) starts from that empty default and writes the **whole** state on the first change. Every way out of onboarding writes, because Skip ends in `completeOnboarding()`.
- **Steps:** a shopper has `preferences.v1` = onboarded, city Lahore, followed brands, and Urdu. At launch one DataStore/SharedPreferences read throws (I/O error, a corrupted locale entry, or the platform channel not ready). Then:
  1. the app opens on `/welcome` in the phone language;
  2. the shopper taps through (Continue, Skip ×3, Not now);
  3. `preferences.v1` now reads `{"onboarded":true,"city_id":null,"interest_ids":[],"brand_ids":[]…}`.
- **Expected:**
  - `docs/app/ONBOARDING.md`: "A damaged file reads as a first launch, field by field", but a *read error* is not a damaged file.
  - Guest-first follows live only on the phone (until 4.2), so they must not be overwritten because a read failed.
  - A locale read failure alone must not hide readable preferences.
- **Actual:** the saved city, interests and follows are lost for good. A failure reading only the locale also hides the preferences: the shopper is re-onboarded and their data overwritten.
- **Evidence:** `test/qa/onboarding_qa_test.dart`, group "persistence":
  - "a transient read failure at launch does not wipe a returning shopper's saved choices" fails with `Expected: ['brand-a', 'brand-b'] Actual: []`;
  - "a failure reading the language alone does not hide the saved preferences" fails (opens on `/welcome`, not Home).
- **Severity rationale:** this is data loss of the shopper's only copy (S1 by the letter). Graded **S2** because it needs a prior storage read failure, which is uncommon. It is still release-blocking.
- **Suggested fix:**
  - read the locale and the preferences in separate `try`s;
  - on a preference read *error* (not a parse error), retry once. If it still fails, keep the store but mark the preferences "unknown", and don't write them until a read succeeds; or start from defaults in memory only for the session;
  - keep writes field-level (merge with what is stored) instead of replacing the whole document.

### BUG-2 (S3): Location errors escape the service; "Detect my city" spins forever
- **Area / file:** `lib/core/device/location_service.dart:91-102` catches only `PermissionDeniedException`, `LocationServiceDisabledException`, `TimeoutException`, `MissingPluginException` and `PlatformException`.
- **Why that's not enough:** geolocator's method channel converts platform errors into its **own** exception classes, none of which is a `PlatformException`: `PositionUpdateException` (LOCATION_UPDATE_FAILURE), `ActivityMissingException`, `PermissionRequestInProgressException`, `PermissionDefinitionsNotFoundException` and `InvalidPermissionException` (`geolocator_platform_interface-4.4.1/lib/src/implementations/method_channel_geolocator.dart:229-250`).
- **What the user sees:** `CityStep._detect` (`city_step.dart:42-71`) has no `try`. The error escapes to the zone as an uncaught error, and `_detection` stays `detecting`: a spinner and a disabled "Detect my city" for the rest of the step. The list and Skip still work, which is the workaround.
- **Expected:** "Both turn every platform error … into an outcome; neither ever throws" (`ONBOARDING.md`).
- **Evidence:** `onboarding_qa_test.dart`, group "location outcomes": 5 service tests (one per exception) plus "the city step recovers when the location call fails" fail in known-bug mode (`PositionUpdateException … was thrown`).
- **Suggested fix:**
  - in the service, add `on Exception { return const LocationUnavailable(); }` after the specific clauses;
  - make `PermissionRequestInProgressException` an outcome (or ignore it);
  - in `_detect`, use `try/finally` so the state always leaves `detecting`.

### BUG-3 (S3): An unused location foreground service is merged into the app
- **Area / file:** `android/app/src/main/AndroidManifest.xml` removes fine and background location (`:14-15`) but not the service that `geolocator_android-5.2.1/android/src/main/AndroidManifest.xml` declares: `<service android:name=".GeolocatorLocationService" android:foregroundServiceType="location" android:exported="false"/>`.
- **Why it matters:**
  - The app never starts it (one-shot `getCurrentPosition`, no background updates).
  - Google Play requires a foreground-service declaration (with a video) for every FGS type in the manifest of an app targeting API 34+.
  - A `location` FGS is a sensitive type and contradicts the Data safety story ("used once for a nearest-city lookup").
- **Evidence:** `test/qa/merged_manifest_qa_test.dart` "no location foreground service is merged in" fails: `['geolocator_android: .GeolocatorLocationService (location)']`. The merged-permission test passes. The merged set is INTERNET, ACCESS_COARSE_LOCATION, POST_NOTIFICATIONS, plus ACCESS_NETWORK_STATE from connectivity_plus.
- **Note:** `android_config_test.dart` checks only the app's own manifest, so it can't see this. Maven dependencies (`play-services-location`) weren't merged here; check `merged_manifests/*Release` in CI.
- **Suggested fix:** add `<service android:name="com.baseflow.geolocator.GeolocatorLocationService" tools:node="remove"/>` to `<application>`. Extend the manifest lint to read the merged manifest in CI.

### BUG-4 (S4, condition): An existing migration was edited
- **Area / file:** `supabase/migrations/20261029120100_reference_data.sql:14-18` gained the `center_lat`/`center_lng` generated columns inside the original `create table`, against `docs/backend/SCHEMA.md:68`: "never edited after they reach a shared environment; add a new migration instead".
- **Impact:**

  - The columns then don't exist, so `cities()` fails (`column center_lat does not exist`) and the city step shows only "Try again".
  - `tool/db_test.sh` passes only because it builds from zero.
- **Suggested fix:** move the two columns to a new migration, `alter table public.cities add column … generated always as (…) stored`.
- **Escalation:** **S2** if any shared environment exists.

### BUG-5 (S4): `/welcome/<step>` links skip the language step
- **Area / file:** `lib/app/router/app_router.dart:24-27`: `if (inWelcome) return null;` lets any `/welcome/...` location through before onboarding.
- **Steps:** first launch via a link (or a web URL) to `/welcome/alerts`, then tap "Not now".
- **Expected:** "Language … can't be skipped" (ONBOARDING.md).
- **Actual:** the app lands on step 5 with no back stack, and "Not now" ends onboarding. Language stays the phone default and the city is never offered.
- **Evidence:** "a link straight to /welcome/alerts cannot skip the language step" (skipped reproducer).
- **Suggested fix:** while not onboarded, redirect any `/welcome/<sub>` that isn't the top of the current stack to `/welcome`. Or allow only `/welcome` as an entry location.

### BUG-6 (S4): Same-frame double taps act twice
- **Area / file:**
  - `language_step.dart:67` and the `next()` pushes in `city_step.dart`, `interests_step.dart` and `brands_step.dart` push without a guard;
  - `alerts_step.dart:29-30` (`_turnOn`) and `city_step.dart:42-43` (`_detect`) are disabled only after the next rebuild.
- **Scope:** a real double tap 100 ms apart is safe (QA tests pass: the route transition ignores pointers, and the buttons disable). Two pointer events in one frame, such as a two-finger tap, push the city step twice or call `request()` twice.
- **Why the second call can hurt:** on Android it's a `PlatformException` ("already running"), mapped to "unavailable", so onboarding finishes while the system dialog is still up.
- **Evidence:** "same-frame double tap on … acts once" ×2 (skipped reproducers).
- **Fix:** a `_busy` flag set synchronously before the first `await` and before `push`.

### BUG-7 (S4): Web notification path
- **What happens:** on the web, `permission_handler_html` maps the browser's denied state to `permanentlyDenied`. The step then says "Alerts are blocked for this app…" and offers **Open settings**, which does nothing on the web (`openAppSettings` → false) before onboarding ends.
- **Evidence:**
  - with no permission (headless default): `flow_en-PK_2_after_alerts.png`, onboarding not finished until Continue;
  - with notifications granted in the browser context, the flow completes and opens the pending deal (`flow_en-PK_granted_2_after_alerts.png`, URL `/deal/<uuid>`).
- The app is Android-first; recorded so the web demo doesn't mislead.

  - Your two reproducers are un-skipped and pass.
- **BUG-2 (S3), fixed.** `GeolocatorLocationService` maps every other error to `LocationUnavailable`, and `CityStep._detect` has its own `try` and a re-entry guard, so the button never stays spinning. Reproducers un-skipped.
- **BUG-3 (S3), fixed.** `AndroidManifest.xml` removes `com.baseflow.geolocator.GeolocatorLocationService` (`tools:node="remove"`). Your merged-manifest test is un-skipped and passes.
- **BUG-4 (S4), documented, not changed.** Nothing has been deployed, so migrations are still edited in place. `SCHEMA.md` and `RELEASE.md` now say they freeze at the first `db push`.
- **BUG-5 (S4), fixed.** `languageChosenProvider`: either a saved language, or Continue on the first step. Until then any `/welcome/<step>` redirects to `/welcome`. Your reproducer passes, and harnesses that open a step directly now confirm the language first (`languageChosen: true` by default, `false` in the BUG-5 test).
- **BUG-6 (S4), fixed.** `OnboardingScaffold` lets one tap per frame through each action, and the alerts handlers guard re-entry. Your same-frame reproducers pass.
- **BUG-7 (S4), fixed.** On the web there's no "Open settings": the city step hides it, and the alerts step shows the blocked note and finishes.
