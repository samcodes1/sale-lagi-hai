### 4.6-S3 (S3): "50%+ off" also returns "Up to 50% off" sales
- **Area / file:** `supabase/migrations/20261029220000_search.sql:28` (`percent >= …` for every `offer_kind`); the demo mirrors it in `demo_gateway.dart` `_passesSearchFilters`.
- **Steps:** on Search, tap the **50%+ off** quick chip, or pick 50%+ in the sheet.
- **Expected:** at least 50% off, as API.md describes it ("at least a percentage off").
- **Actual:** "Threads (Demo) Winter collection sale, **Up to 50% off**" is listed (`offer_kind = up_to_percent_off`). Its discount is at most 50%, and most items are usually less. Workaround: read the badge.
- **Evidence:** `docs/qa/screens/4.6/filtered_360x800_light_en.png`; `qa_search.test.sql` "QA BUG 4.6-S3" (fails: 1 row, expected 0).
- **Suggested fix:** for `min_percent`, accept `percent_off` and `flat_percent_off` only. Or keep "up to" offers but say so in the chip ("Up to 50%+ included") and sort them after real ones. That is a product decision, so state it in SEARCH.md either way.

### 4.6-S1 (S4): with words, the list ends if the page's last deal ends or is hidden before the next page
- **Area / file:** `search.sql:134-136`. The words branch finds the cursor row only inside the recomputed live hits.
- **Steps:** search "wombat" with page size 2. The second deal on page 1 then ends (or is hidden by moderation, or is pushed past the 250 cap). Ask for page 2.
- **Expected:** the next page follows; the filters-alone branch does this, because it reads the cursor from `public.deals`.
- **Actual:** an empty page, so the list silently ends ("That's every live deal here"). This is documented, but it shows up most where "Ending soon" is on. Workaround: pull to refresh.
- **Evidence:** `qa_search.test.sql` "QA BUG 4.6-S1" (todo; have 0, want 2).
- **Suggested fix:** compute the cursor's `(rank, published_at, id)` from the deal row itself, whether it is live or not, using the same rank expression. Or let the client send the cursor's rank with `after_id`.

### 4.6-S2 (S4): an area filter keeps every online and nationwide match, so the area's own deals can fall past the cap
- **Area / file:** `search.sql:21-24`, with `order by 2 desc, d.id … limit 250` at `:89-90`.
- **Steps:** with 300 nationwide matches that rank above or alongside one Clifton deal, search with area = Clifton.
- **Expected (shopper):** "Clifton" shows Clifton deals, or at least shows them first.
- **Actual:** 250 results. The Clifton deal is past the cap and never appears, and the filter barely narrows the list. The semantics match the docs ("online and nationwide stay"), so this is S4.
- **Evidence:** `qa_search.test.sql` "QA BUG 4.6-S2" (todo), plus the passing "area keeps online and nationwide deals…" (250).
- **Answer to "is that what a shopper expects?":** partly. Keeping online and nationwide deals is right; they are available in Clifton. City-wide local deals are right too. But they should come after the area's own deals. Suggested: when `area` is set, order area-targeted local deals first, then city-wide, then online and nationwide; or add an "Only in Clifton" switch.

### 4.6-A1 (S4): a search saved before the recent list has loaded overwrites the older searches on the phone
`search_providers.dart:161` (`add` → `_save` with the not-yet-loaded state). The in-memory list merges once the read finishes, but the file holds only the new words until the next change. If the app is closed first, the older recent searches are gone. This is likeliest when a `?q=` link opens Search, since it submits on the first frame. Reproducer: `search_qa_test.dart` "QA BUG 4.6-A1" (skipped; fails unskipped: file `['new one']`). Fix: make `add`, `remove` and `clear` await the load future (keep it in a field) before saving.

### 4.6-A2 (S4): saved deals still log a FormatException that quotes the stored list
`lib/features/saved/application/saved_providers.dart:45-48` logs the error object. For a corrupt `saved.v1`, the `FormatException`'s text quotes the stored ids of what the shopper saved; this is the pattern the developer fixed in `RecentSearches`. The other `error:` log sites were checked: JSON cache (public deal data), preferences (`PreferencesStore.read` catches `FormatException` itself), secure storage (codes only), bootstrap and locale. They are fine. Reproducer: `search_qa_test.dart` "QA BUG 4.6-A2" (skipped; fails unskipped). Fix: log `error.runtimeType` only, as in `search_providers.dart:147`.

### 4.6-A3 (S4): suggestion and recent-search rows aren't announced as buttons
`search_screen.dart:350-416`: `_Row` is an `InkWell` with a tap action but no `isButton` flag, so TalkBack reads "Karahi House (Demo), Brand" without "button". The quick chips and sheet chips are fine: label, button and selected state. Reproducer: "QA BUG 4.6-A3" (skipped). Fix: wrap the row in `Semantics(button: true, …)`.

### 4.6-A4 (S4): `/search?q=` cut at 100 UTF-16 units can split an emoji
`routes.dart:213`: `words.substring(0, 100)` can leave a lone surrogate, which shows as a broken character and is sent to the server as an invalid code point. The field's own 100 limit counts characters, so it is not affected. Reproducer: "QA BUG 4.6-A4" (skipped). Fix: cut by runes or characters (`words.characters.take(100)`).

### 4.6-A5 (S4): the words-only empty state says "or clear the filters" when none are on
`emptySearch` ("No deals for “zzqqxx”. Try another word or clear the filters.") shows with no filters, and there is correctly no Clear filters button. Evidence: `search-empty_*` shots in the flow sheets. Fix: a second string for the no-filters case.

### 4.6-A6 (S4): every search keeps its result pages and suggestions for the rest of the session
`dealListProvider` (`deal_list.dart:126-130`) and `searchSuggestionsProvider` are families that aren't auto-disposed. Every settled query keeps up to 250 deals and its brand list in memory, and typing an earlier query again shows the old pages, possibly expired, without asking the server. Fix: `.autoDispose` for search lists and suggestions, or a small LRU.

## Backend review
- **Paging** (`qa_search.test.sql`, all passing unless marked):
  - **Ties:** a 300-way tie on rank and `published_at` walks to exactly 250, with none twice, in the same order at page size 7 as at 50.
  - **Filters alone with ties:** each deal comes once.
  - **A new best match mid-walk:** it is not slipped in, and the remainder is unchanged.
  - **An `after_id` from another search:** with words it ends the list, with no leak and no repeat. Without words it is only a `published_at` cursor, which is harmless because the app never mixes cursors (`SearchDeals` is the provider key).
  - **The cursor deal ends:** S1.
- **Filters before the cap:** the developer covered `min_percent`. QA checked bank, ending-soon and category: each finds its one narrow match behind 300 better ones, where a control without filters does not. Area is the exception by design (S2).
- **Area edges:**
  - an area of another city, with the shopper's city, matches only a deal that targets both cities;
  - an unknown area keeps online and nationwide deals only;
  - an area without a city keeps local deals hidden, as everywhere;
  - `min_percent` 0 is clamped to 1.
- **Injection (`%L` in `search_hits` and `brand_hits`):**
  - These 14 hostile inputs neither error nor return drafts: quotes, `'); drop table … --`, `$q$ union …`, `%1$L`, `%%`, `\`, `\'`, a tab, RLO, `*:`, `!!`, 100 characters.
  - The deals table survives.
  - The typed arguments (uuid, uuid[], integer) also go in through `%L` with casts, so they are safe.
- **`brand_suggestions`:**
  - a backslash, a quote, `%` and `_` (the last two from the developer) match as themselves;
  - a lone `\` matches nothing;
  - page size is clamped (100 → 10, 0 → 1, null → 6);
  - blank or null words return nothing;
  - a business owner can read their own hidden brand under RLS, but it is never suggested by English or Urdu name;
  - `brand_hits` returns only active brands' ids, and the RPC reads brands under the caller's RLS;
  - `private` isn't an exposed schema (`config.toml` `schemas = ["public"]`), so the definer helpers aren't callable over the API.
- **Plans:** `210_query_plans` shows no seq scans of `deals` for a filtered search and for filters alone, and no seq scan of `brands` for suggestions over 20,000 brands. The new `brands_name_ur_trgm_idx` serves the Urdu prefix.
- **The developer's edits to earlier tests are faithful:**
  - `200_read_apis`: the hostile-words `lives_ok` now uses a random `after_id` in place of `page => 99`, with the same intent.
  - `qa_read_apis`:
    - "pages stop at page 4" became "a page after a deal not in the results is empty". The cap it guarded is now checked by QA's 250-walk.
    - The two count checks just use named `page_size`.
  - `qa_phase2_roles`: `brand_suggestions` is pinned; the matrix adds `search_filters` and `brand_suggestions` (108 = 6 roles × 18).
  - `010_schema`: the two new private helpers are listed.

## Privacy review
- Recent searches stay on the phone (`search.recent.v1`, 8 max). Load and save failures log only the error type, and a failing save logs no searched words (QA test). Clearing local data on account deletion removes them.
- Searches reach the server only as RPC parameters (POST bodies, not URLs), and nothing in 4.6 stores them.
- Sibling leak: A2. `SearchFilters.toString()` holds no ids (QA test).
- Note for Phase 5.3: a `/search?q=` link writes its words into the shopper's recent searches. Once inbound deep links exist, consider searching without saving words that came from a link, so links can't plant text in someone's history.

## Recommendations (non-blocking)
1. **ActionChip semantics.** "Filters" is an `ActionChip` that the framework exposes with `hasSelectedState`, so the web tree calls it a checkbox. On Android it reads as a button, but a plain `FilledButton.tonal` or `InputChip` would read cleanly everywhere.
2. **Length checks.** The client checks length in UTF-16 units (`backend_deal_repository.dart`, `words.length > 100`), the server in characters, and the field in grapheme clusters. Emoji-heavy words can be refused on the phone that the server would take. Use `characters.length` on the client.
3. **Function search_path.** `private.matches_search_filters` has no pinned `search_path`. It is invoker-rights and fully qualified, so it is safe, but pinning it like the other helpers keeps the lint rule uniform if it ever becomes definer.
4. **Edits to applied migrations.** 4.5 edited 4.2's migration in place (noted in 4.2's report). 4.6 correctly adds a new migration; keep that rule.
